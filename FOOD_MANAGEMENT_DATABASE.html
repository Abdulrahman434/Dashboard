i Overview

How the data is organised and how to read this document.

◆
The module lets a hospital dietary team build meal menus that adapt per diet type (Regular, Diabetic, Low sodium…), per meal (Breakfast/Lunch/Dinner), and per day of week. Patients (or nurses) place meal orders from the currently published menu, and orders flow through a kitchen queue (Submitted → Printed → Delivered).

The 20 tables fall into four groups:

1 · Reference data — allergens, meals, sections, diets, service window 2 · Dish catalog — dishes + allergens, patient groups 3 · Menu sets — sets, rules, per-day dish lists 4 · Operations — patients, orders
PK primary key FK foreign key UQ unique NN not null IX indexed reference core junction operational

◈ Relationship map

Cardinality of the main entities. ──< means "one-to-many".

meals ──< meal_sections >── menu_sections (which categories appear in each meal) menu_sections ──< dishes ──< dish_allergens >── allergens menu_sets ──< menu_set_diets >── diets menu_sets ──< menu_set_meals >── meals menu_sets ──< menu_set_groups >── patient_groups menu_sets ──< menu_section_rules (diet × meal × section → min/max/serve-to-all) menu_section_rules ──< menu_day_slots (one row per weekday: default dish) menu_day_slots ──< menu_day_dishes >── dishes diets ──< patients ──< patient_allergies >── allergens patients ──< orders ──< order_lines >── dishes
▲
Menu ownership. In the prototype, every menu set owns its own independent menu tree — editing one set never touches another's dishes or rules. That is why menu_section_rules and its children hang off menu_sets, not off the global sections. Dishes, however, are shared from one catalog.

✦ Implementation notes

Guidance for turning this into a production backend.

Snapshots on ordersOrder rows copy patient_name, room, bed and each line's dish_name_snapshot so a printed kitchen ticket never changes if the patient is discharged or a dish is renamed. Keep the FKs too, for reporting.
One live setEnforce "at most one Published set" with a partial unique index: CREATE UNIQUE INDEX one_published ON menu_sets ((status)) WHERE status='Published';
Menu volumeRules explode as set × diet × meal × section × 7 days. One full set ≈ 8 diets × ~2.4 meals-with-sections ≈ hundreds of rule rows and thousands of menu_day_dishes. All indexed by menu_set_id; fine for Postgres/MySQL.
Regular-diet fallbackThe prototype falls back to the Regular diet's menu when a specific diet has no rows for a meal. Reproduce this in the read query (coalesce to is_regular diet), not by duplicating data.
Allergy safetyFlag a dish as unsafe when dish_allergens ∩ patient_allergies ≠ ∅. Consider a DB view for this.
i18nEvery catalog/reference table carries name_en + name_ar. Arabic is RTL — store as UTF-8, no transformation needed.
HIS integrationdiets.his_code and the suggested patients.mrn are the join keys to the Hospital Information System for diet orders and patient identity.
Soft deletesis_active on dishes/sections/diets mirrors the prototype on toggles — hide instead of deleting to preserve order history.
